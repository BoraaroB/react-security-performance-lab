# PR 07a: Encryption at rest (AES-256-GCM) and generated secrets

## What and why
If a database or backup leaks, sensitive fields should not be readable. This PR adds `lib/crypto`: AES-256-GCM
encryption that also **detects tampering** (a changed value fails to decrypt instead of returning wrong data).
The key comes from a new required env var, `DATA_ENCRYPTION_KEY`, generated by `scripts/setup-env.mjs` with a secure
random generator. The store that uses it comes in 07c. Topic: API security (data at rest, secrets management).

## Changes
- `backend-express/src/lib/crypto/encryption.ts`: `createEncryptor({ key })` → `encrypt(text, context?)` /
  `decrypt(payload, context?)`; `parseEncryptionKey(base64)`; `DecryptionError`, `EncryptionKeyError`.
- `backend-express/src/lib/crypto/index.ts`, `README.md`: exports, usage, notes (IVs, searching, rotation).
- `backend-express/src/app/config.ts`: required `DATA_ENCRYPTION_KEY` (32 bytes, base64), checked at startup.
  The app's shared encryptor is created in 07c, where the store first uses it.
- `backend-express/src/app/routes/demo.ts`: `GET /api/demo/crypto` (fixed text, its own throwaway key: random IV,
  tampering, wrong context).
- `scripts/setup-env.mjs`: creates `.env` from `.env.example` if missing and fills empty secrets; keeps existing values;
  mode 600 before writing; atomic write (temp file + rename).
- `backend-express/.env.example`: `DATA_ENCRYPTION_KEY=` (empty on purpose) + setup instructions.

## How to test
```bash
node scripts/setup-env.mjs   # "DATA_ENCRYPTION_KEY generated"; run again → "already set, kept"
cd backend-express && npm run dev
curl -s localhost:4000/api/demo/crypto
# first ≠ second (random IV), decrypted: "Jane Doe", tampered / wrongContext: "DECRYPTION_FAILED"
DATA_ENCRYPTION_KEY='abc!' npx tsx src/index.ts   # → "must be 32 random bytes in base64", exit 1
```

## How to reuse in another project
Copy `src/lib/crypto/` (no npm packages):
```ts
import { createEncryptor, parseEncryptionKey } from './lib/crypto/index.js';
const encryptor = createEncryptor({ key: parseEncryptionKey(process.env.DATA_ENCRYPTION_KEY ?? '') });
const stored = encryptor.encrypt(user.name, `users.name:${user.id}`);
const name = encryptor.decrypt(stored, `users.name:${user.id}`);
```

## Verification
- `npm run typecheck`, `npm run build`: no errors. Portability grep: only the README example uses `process.env`.
- Temporary script: round trip (incl. empty text and `✓`), same text → different output, wrong context / other key /
  shortened tag / extra part / garbage / `v2` → `DECRYPTION_FAILED`; key with a typo, 16 bytes, empty, base64url →
  `INVALID_ENCRYPTION_KEY`; a raw 16-byte key → rejected.
- `setup-env.mjs` on a scratch copy: new `.env` (mode 600, 44-char key); re-run keeps the key; `export DATA_ENCRYPTION_KEY=...`
  is kept (no second key); `DATA_ENCRYPTION_KEY=""` gets a key; an existing 644 `.env` without the key gets it appended
  and becomes 600; no `.env.tmp` left behind. The real `.env` was not touched.
- Server: no key, empty key, bad key → startup error with the setup hint, exit 1; with a key → demo route as
  expected, `/api/health` 200, key not in the log. `NODE_ENV=production` → `/api/demo/crypto` 404.
- All of the above re-run after the review fixes.
- Size: ~200 lines of code including comments (~140 without), a bit over budget because of the explanations and review fixes.

## Review
Both reviewers confirmed the core: fresh 12-byte IV per value, `authTagLength: 16` on both sides, AAD on both sides,
one generic `DecryptionError` (no oracle), strict key parsing, the key never appears in logs or env errors.
- **Fixed** (both): `setup-env.mjs` wrote the key into a 644 file and only then ran `chmod` (and `mode` in `writeFileSync`
  had no effect on an existing file). Now `chmod 600` comes first, then a temp file is renamed over `.env`, so a crash
  mid-write cannot truncate `.env` and lose an existing key. Nothing is written when nothing changed.
- **Fixed** (security): the demo used the real `DATA_ENCRYPTION_KEY` with a realistic context (`user-1`), so a public
  route handed out ciphertexts the real key accepts. The demo now has its own random key and `demo:` contexts.
  The unused `src/app/crypto.ts` glue was removed; 07c creates it where the store uses it.
- **Fixed** (security): `export DATA_ENCRYPTION_KEY=...` or `NAME = value` was not recognized, so the script would append a
  second, NEW key. The match is now tolerant. (code-reviewer nit) `NAME=""` now counts as empty.
- **Fixed** (code): an empty key (`DATA_ENCRYPTION_KEY=` after `cp .env.example .env`) gave no setup hint. It does now.
- **Fixed** (both): README recommended only the user ID as context; two encrypted columns of the same row could be
  swapped. Now `users.name:${user.id}` (table + column + row).
- **Fixed** (code): README size note was wrong for long values; now "≈ 43 + 4/3 × input bytes".

## Interview questions
1. **Why AES-GCM and not AES-CBC?** GCM is authenticated encryption: the tag detects any change to the ciphertext.
   Plain CBC has no integrity, so a changed value decrypts to garbage (or worse, enables padding-oracle attacks).
2. **What happens if you reuse an IV with GCM?** With the same key, an attacker learns the XOR of both plaintexts and
   can forge tags. That is why every value gets a fresh random 12-byte IV, stored next to the ciphertext (it is not secret).
3. **Encrypt or hash passwords?** Hash (bcrypt/argon2): you never need the password back, only to check it.
   Encrypt data you must read again (names, OAuth tokens). If the key leaks, encrypted data leaks; hashes do not.
